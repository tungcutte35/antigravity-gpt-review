++Problem: Claude response completion is inferred only from the temporary absence of a "Stop" button after a fixed delay, with no check that the extracted text actually contains a final REVIEW_STATUS verdict before the pipeline treats the run as done.
++Evidence: After sending the prompt, the code waits 5s, then polls button[aria-label*="Stop"], button:has-text("Stop response") up to 30 times (90s max) and breaks as soon as neither selector is visible. It then waits another 5s and extracts text via .font-claude-message / div[data-is-streaming] / .grid / .prose, falling back to document.body.innerText if none of those yield >20 chars. The result is written directly to claude_review_response.txt and parsed with resultText.match(/^REVIEW_STATUS:\s*(APPROVED|CHANGES_REQUESTED)\s*$/im), defaulting to 'UNKNOWN' with no retry.
++Failure scenario: If Claude's UI briefly hides the Stop button (e.g. between token chunks), if the aria-label/selector changes, or if the response is still rendering when the loop exits, the script captures a partial or unrelated response. Since test-dual-pr.js uses this exact status (APPROVED/CHANGES_REQUESTED/UNKNOWN) to decide the process exit code that gates the PR (process.exit(0) vs process.exit(1)), a truncated read that happens to omit or mangle the REVIEW_STATUS line silently produces UNKNOWN → CHANGES_REQUESTED, or in a worse case could pick up stray text resembling the pattern from an unrelated part of the page and incorrectly gate a merge decision.
++Recommended fix: After the Stop-button loop, add an explicit poll/retry that only accepts the result once resultText matches the REVIEW_STATUS: pattern (or a bounded number of stability checks show the text is no longer growing between polls), rather than accepting whatever is scraped on the first pass. For example, loop up to the remaining timeout budget re-extracting text every few seconds until the regex matches or the hard timeout is hit, and log/flag explicitly when falling back to UNKNOWN due to timeout so downstream consumers can distinguish "no verdict produced" from "explicit CHANGES_REQUESTED."

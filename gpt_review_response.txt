File: test-dual-pr.js
Problem: A failed ChatGPT Stage 1 can cause Claude Stage 2 to consume a stale gpt_review_response.txt from a previous run, making the final verdict depend on an unrelated historical review.
Evidence: Stage 1 errors are caught and execution continues: catch (gptErr) { ... Proceeding to Stage 2 with diff context only... }. However, Stage 2 always calls runClaudeReview({ gptResponseFilePath: 'gpt_review_response.txt', ... }), and runClaudeReview() loads that file whenever it exists. There is no deletion, truncation, or run-specific validation of the file when Stage 1 fails.
Failure scenario: Run the dual pipeline successfully once, producing gpt_review_response.txt. On a subsequent run, ChatGPT fails before producing a new response (CDP/UI failure, timeout, etc.). The old file remains, Stage 2 loads it, and Claude receives the current diff combined with stale findings from the previous PR/review. Claude can therefore confirm or reject findings based on obsolete evidence while the console claims it is proceeding with "diff context only."
Recommended fix: Make the Stage-1 result explicit and only pass its response to Claude when it was generated during the current invocation. For example, initialize/remove the output before Stage 1, then pass gptResponseFilePath: null or an in-memory gptResult.resultText when Stage 1 fails. Prefer passing the Stage-1 response directly to runClaudeReview() rather than using a persistent filename as implicit state.

Problem: Claude response completion is inferred solely from the presence/absence of a UI-specific Stop button, with no validation that the extracted response contains the required final verdict before the pipeline treats the run as completed.
Evidence: After a fixed 5-second delay, the loop checks only button[aria-label*="Stop"], button:has-text("Stop response"). If neither selector matches, the loop immediately proceeds to response extraction. The extraction then falls back to document.body.innerText, and the status parser converts any response without the exact REVIEW_STATUS line to UNKNOWN.
Failure scenario: Claude changes its DOM/ARIA label, the Stop button is temporarily absent, or the response is still streaming while the selector is unavailable. The script reads a partial response, writes it to claude_review_response.txt, parses UNKNOWN, and terminates with a rejected review even though Claude may subsequently produce the required verdict. This makes the automated gate dependent on an unstable UI implementation detail.
Recommended fix: Track the submitted prompt and wait for a new assistant response whose text stabilizes across successive polls, or wait for a known Claude completion state. After extraction, explicitly require REVIEW_STATUS: APPROVED|CHANGES_REQUESTED; otherwise continue polling until the timeout rather than immediately treating a partial/unknown response as the final result.
